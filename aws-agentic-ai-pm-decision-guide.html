Decision 02

1. The one system problem that organizes the day

Assume a company wants an internal operations assistant on AWS. It must:

  1. answer employee questions from SharePoint, Confluence, PDFs, policies, and selected operational records;
  2. cite the evidence used;
  3. read current order or customer data through enterprise APIs;
  4. propose a refund or case update;
  5. require approval for high-impact actions;
  6. execute only within the user's authority;
  7. survive retries and partial failures without duplicate side effects;
  8. expose enough traces, quality scores, latency, and cost data for a PM to diagnose failure.

This is deliberately one system. RAG, tools, MCP, agents, Lambda, API Gateway, Step Functions, S3, DynamoDB, IAM, AgentCore, and observability are learned as boundaries inside it—not as unrelated products.

Decision 05

4. RAG: the depth a PM actually needs

RAG is two products joined together

  1. Retrieval product: Given a user query and their permissions, return the smallest set of evidence that contains the answer.
  2. Generation product: Given the question and retrieved evidence, produce a useful answer that remains faithful to that evidence.

If the answer is wrong, first ask whether the correct evidence was retrieved. Do not let a team hide retrieval failure inside one end-to-end “accuracy” number. Bedrock evaluations support retrieval metrics such as context relevance/coverage and generation metrics such as faithfulness, correctness, and completeness. AWS: Bedrock Evaluations and AWS: Evaluate and improve Knowledge Bases

The seven levers of a better knowledge base

  1. Source quality and ownership. Name the authoritative source, owner, update frequency, deletion policy, and conflict rule. More documents can reduce quality when copies contradict one another.
  2. Parsing. Tables, slides, scanned PDFs, images, audio, and video require more than plain text extraction. Managed Knowledge Bases now includes Smart Parsing and multimodal support; customer-managed pipelines require you to own these choices. AWS: Knowledge Bases overview
  3. Chunking. Fixed chunks are easy; semantic or hierarchical chunks better preserve meaning in complex documents. Chunk size and overlap are evaluation variables, not universal best practices. AWS: Advanced parsing, chunking, and query reformulation
  4. Metadata and filters. Add fields that support real product constraints: tenant, department, document type, effective date, geography, policy status, sensitivity, and version. Filters are often more important than a marginal embedding-model improvement.
  5. Retrieval mode. Semantic search finds meaning; keyword search catches exact entities, codes, names, and prices. Hybrid search combines them where supported. AWS: Hybrid search
  6. Reranking and query decomposition. Retrieve a wider candidate set, rerank it for relevance, and break multi-part questions into subqueries when necessary. Reranking can reduce the number of chunks passed to the model, improving relevance and potentially latency/cost. AWS: Reranking and AWS: Query configuration
  7. Authorization and freshness. A relevant document is still wrong if the user may not see it or if it is superseded. Bedrock's SharePoint ACL feature filters and verifies access, but AWS explicitly says ACL awareness is not authentication; the application must authenticate the user and supply verified identity context. AWS: SharePoint document-level access controls

The PM acceptance scorecard for RAG

Ask the team for a versioned evaluation set with representative questions, expected evidence, allowed abstentions, user/tenant identities, and known edge cases. Review at least these measures:

  • retrieval hit: did any returned chunk contain the required evidence?
  • context relevance: how much retrieved material was useful rather than noise?
  • context coverage: did the evidence cover every part of the question?
  • citation correctness: does each citation support the adjacent claim?
  • faithfulness: is the answer supported by retrieved evidence?
  • completeness: were all required parts answered?
  • abstention quality: did the system decline when evidence was missing or unauthorized?
  • freshness: did a changed or deleted source propagate within the agreed window?
  • permission correctness: were forbidden documents absent from retrieval and logs?
  • p50/p95 latency and cost per successful answer: averages hide tail pain and repeated retrieval loops.

Three diagnostic examples

Decision 06

5. Vector databases: what to decide, not how to tune an index

Does Amazon have a vector database?

Yes—several AWS services support vector search, and Amazon S3 Vectors is an AWS-native purpose-built vector storage and query capability. The answer is not “pick the Amazon vector database,” because the options serve different workloads.

Bedrock Knowledge Bases currently lists these supported vector stores: Amazon OpenSearch Serverless, OpenSearch managed clusters, Amazon Neptune, Amazon Aurora, Pinecone, Redis Enterprise Cloud, MongoDB Atlas, and Amazon S3 Vectors. AWS: Supported data and vector stores

PM decision table

Option Choose when Watch-outs / evidence needed
Bedrock Managed Knowledge Base speed, managed operations, enterprise connectors, smart parsing, agentic retrieval, and predictable ownership matter more than custom pipeline control validate current region/features, connector ACL behaviour, retrieval quality, and cost on your corpus
S3 Vectors very large, cost-sensitive vector collections can tolerate sub-second rather than ultra-low latency; semantic search is enough current Knowledge Bases integration supports semantic search but not hybrid search; check metadata limits and workload latency AWS: S3 Vectors with Bedrock KB
OpenSearch Serverless / managed hybrid keyword+vector search, filters, search analytics, and more query control matter cluster/serverless cost, operations, index tuning, and capacity behaviour
Aurora PostgreSQL + pgvector relational joins, transactions, SQL, and vectors belong together scaling and vector-search performance must be tested on the real query/data distribution
Neptune / Neptune Analytics relationships are first-class and GraphRAG or multi-hop relationship traversal is essential graph modelling and operations are justified only if graph questions matter
MongoDB Atlas the product already uses MongoDB documents and wants vector search in that ecosystem third-party commercial/operational boundary and exact Bedrock integration support
Pinecone / Redis Enterprise Cloud an existing platform standard, team expertise, or workload requirement justifies it external vendor, networking, identity, data residency, and cost boundary
DocumentDB / MemoryDB AWS-native MongoDB-compatible or very-low-latency application patterns need vector capability outside the simplest KB integration path do not imply direct Bedrock Knowledge Bases support unless current documentation confirms it

Top-PM default: start with Managed Knowledge Base or a supported managed store, then earn the complexity of a custom vector architecture with an explicit failing requirement. “We might need control” is not a requirement.

Decision 07

6. Agents and AgentCore: understand the production boundary

Bedrock versus AgentCore

  • Bedrock supplies and governs model capabilities: inference, models, Guardrails, Knowledge Bases, and evaluations.
  • AgentCore supplies the production environment around agents: Runtime, Gateway, Identity, Memory, Policy, Observability, Evaluations, Browser, and Code Interpreter. It works with models and frameworks both inside and outside Bedrock. AWS: AgentCore overview

AgentCore modules as PM decisions

Module Product question Failure if ignored
Runtime Does the workload need isolated, stateful, long-running agent execution? fragile custom hosting, session leakage, poor scaling
Gateway How are tools discovered, authenticated, authorized, versioned, and observed? hard-coded integrations, credential sprawl, invisible tool calls
Identity Is the agent acting as the service, the end user, or a delegated user? excessive privilege or broken SaaS access
Policy What actions and parameters are deterministically forbidden? prompt-only authorization and privilege escalation
Memory What may persist within and across sessions? privacy leakage, false personalization, memory treated as truth
Observability Can one user outcome be traced across model, retrieval, tools, policies, and downstream calls? “the agent was weird” with no diagnosable cause
Evaluations What counts as task success, correct tool use, and safe behaviour before and after launch? demo-driven shipping and silent production regression

AgentCore Runtime provides dedicated microVM session isolation in its serverless mode, but the application still owns session-to-user mapping, input validation, dependency security, IAM permissions, and network configuration. AWS: AgentCore Runtime security

Memory is not a database shortcut

AgentCore Memory distinguishes short-term raw interaction events from long-term extracted memories. Long-term memory generation is asynchronous and can store summaries, facts, or preferences under namespaces. AWS: AgentCore memory types

Use this rule:

  • Agent memory: “Rishi prefers a concise weekly report.”
  • DynamoDB or enterprise system of record: “Refund 78491 is approved for ₹12,000.”

Never let extracted memory become the authoritative source for money, entitlements, compliance state, inventory, or customer records.

Multi-agent in one paragraph

Do not start with multiple agents. Add a specialist agent only when one bounded role needs a different tool set, context, model, security boundary, or quality objective—and when a measurable test shows the split improves the outcome. Multi-agent adds handoffs, context duplication, latency, cost, permissions, trace complexity, and new failure modes. AWS's current Agentic AI Lens explicitly calls for role/success/handoff definitions, atomic tasks, secure inter-agent communication, fallback mechanisms, and cost attribution. AWS Well-Architected: Agentic AI Lens

Decision 08

7. Enterprise integrations: API, tool calling, and MCP

First separate three ideas

  1. API: the actual contract used to ask a system for data or cause an action.
  2. Tool calling: the model emits a structured request naming a tool and arguments; application code validates and executes it.
  3. MCP: a standard client/server protocol for discovering and invoking tools and accessing resources/prompts across AI hosts.

MCP does not replace the enterprise API. It normally wraps or exposes a curated part of that API. AgentCore Gateway can translate OpenAPI, API Gateway REST APIs, Lambda functions, Smithy models, MCP servers, and connectors into a consolidated MCP tool surface. AWS: AgentCore Gateway core concepts

Is API or MCP more reliable in real time?

Architecture answer: neither is inherently “more reliable.” A direct API can have fewer hops and is often the lower-risk choice for one stable, latency-sensitive integration. MCP adds a standard discovery/invocation layer and central governance, which becomes valuable across many tools and agents. The underlying API, authentication, idempotency, timeouts, retries, quotas, and downstream availability still determine whether the action succeeds.

Situation Prefer Why
One internal service calls one stable API in a deterministic workflow direct API/SDK fewer moving parts; explicit contract; easiest latency budget
Many agents need a governed catalogue of tools across APIs and SaaS systems MCP through AgentCore Gateway one discovery surface, protocol translation, credential providers, policy, semantic tool search, and observability
Existing REST estate must become agent-accessible API Gateway/OpenAPI as an AgentCore Gateway target preserve existing APIs while presenting curated MCP tools AWS architecture pattern
High-impact action such as payment, refund, or access change either transport, plus deterministic policy/workflow and approval transport choice cannot replace authorization, idempotency, or human oversight
Streaming progress from a long tool MCP/HTTP with supported streaming or an application streaming channel verify current client/server compatibility and end-to-end timeouts

Recommended enterprise pattern: keep APIs as systems of record; expose a small, semantically clear, least-privilege subset as MCP tools through AgentCore Gateway; use direct APIs for deterministic backend steps; never expose a generic “call any URL” or “run arbitrary SQL” tool to an agent.

The tool contract a PM should review

For every tool, ask for:

  • a precise name and description that state when it should and should not be used;
  • typed input and output schemas;
  • read-only versus side-effect classification;
  • the caller identity and downstream identity;
  • least-privilege scope and parameter-level policy;
  • timeout, retry, backoff, quota, and circuit-breaker behaviour;
  • an idempotency key for side effects;
  • validation before execution and sanitization after execution;
  • human approval threshold;
  • audit fields: user, tenant, session, trace, tool, arguments hash, policy decision, result, latency, and error;
  • versioning and deprecation plan.

AgentCore Gateway supports IAM or JWT inbound authorization and multiple outbound credential patterns. AWS recommends real authorization at the gateway/policy/interceptor/target; NONE and authenticate-only configurations do not themselves authorize tool calls. AWS: Gateway inbound authorization

AgentCore Policy uses Cedar with default-deny and forbid-overrides-permit semantics, so policies can reject unsafe tool calls outside the model's prompt. AWS: Cedar policy model

Decision 09

8. How the traditional AWS services fit around the AI

Lambda versus AgentCore Runtime

  • Use Lambda for bounded tools, adapters, validators, and short event handlers.
  • Use AgentCore Runtime for the stateful or long-running agent loop, session isolation, and framework execution.
  • A Runtime-hosted agent can call Lambda tools through AgentCore Gateway.

Lambda can retry events and process the same event more than once, so side-effecting functions must be idempotent. AWS recommends timeouts, backoff with jitter, concurrency controls, metrics/alarms, and awareness of downstream throughput. AWS: Lambda best practices

Step Functions versus LangGraph

  • Use Step Functions for a durable, cross-service business process: explicit states, retries, waits, approval, compensation, and operational history.
  • Use LangGraph for stateful orchestration inside an AI application: agent nodes, branching, checkpointing, pause/resume, and human-in-the-loop around model/tool behaviour.
  • They can coexist: LangGraph handles the conversational/agent loop; a tool starts a Step Functions workflow for an approved multi-system process.

Step Functions has optimized integrations with Bedrock and other AWS services. AWS: Bedrock integration with Step Functions

API Gateway versus AgentCore Gateway

  • API Gateway is a general app/API front door with routing, authentication options, throttles, quotas, and REST/WebSocket capabilities.
  • AgentCore Gateway is an agentic traffic and tool boundary with MCP aggregation/translation, tool discovery, credential providers, agent/HTTP/inference targets, and policy integration.
  • Existing API Gateway APIs can become targets behind AgentCore Gateway rather than being rebuilt.

API Gateway throttles are protective targets, not guaranteed ceilings; clients still need retry discipline. AWS: API Gateway throttling

S3 versus DynamoDB versus Memory

Need Use
versioned documents, uploads, evaluation datasets, batch artifacts S3
operational key/value state, run status, idempotency keys, durable workflow metadata DynamoDB
conversational continuity and selected extracted preferences/summaries AgentCore Memory
semantic retrieval over enterprise content Bedrock Knowledge Base + vector layer

9. Frameworks: learn their decision value, not their syntax

The framework is not the architecture. Your durable product assets are the contracts, test cases, policies, traces, data model, and failure handling. Framework code can change.

Framework What it is for Choose when PM warning
LangChain high-level agent/application abstractions and a large integration ecosystem the team wants fast assembly across models, tools, loaders, and vector stores ease of starting can hide implicit behaviour; insist on explicit tool, state, prompt, and trace contracts LangChain overview
LangGraph low-level graph runtime for long-running, stateful agent workflows with durable execution and human-in-the-loop pause/resume, checkpointing, branching, recovery, or inspectable state transitions are core requirements a graph does not supply business authorization, evaluation quality, or deployment security LangGraph overview
Langfuse LLM/agent observability, tracing, prompt management, datasets, experiments, and evaluations the team needs vendor-neutral/self-hostable AI traces and quality operations beyond basic infrastructure metrics it is primarily an observability/evaluation platform, not the agent orchestrator Langfuse overview
LlamaIndex data-centric RAG, connectors, indexes, retrieval, and agent/workflow abstractions data ingestion/retrieval is the product's hardest differentiator or the team already uses the ecosystem do not choose only because “we are doing RAG”; Managed Knowledge Bases may remove much of the undifferentiated work LlamaIndex MCP overview
Semantic Kernel Microsoft's SDK for AI services, plugins/function calling, agents, and orchestration in C#, Python, and Java the organization is Microsoft/.NET-heavy or its plugin and orchestration model aligns with existing systems verify feature maturity; some agent/memory capabilities are experimental and older group-chat APIs have been superseded Microsoft: Semantic Kernel agent architecture
Strands Agents AWS-backed open-source agent framework with Bedrock/AgentCore, MCP, A2A, and multi-agent patterns an AWS-first team wants a current framework aligned with AgentCore it is missing from the JD, which is another signal that the JD's service map predates current AWS guidance AWS Agentic AI Lens

A practical selection rule

  1. Start with no framework decision.
  2. Write the workflow, state, tool, authorization, approval, recovery, and trace requirements.
  3. Pick the smallest framework that removes a demonstrated engineering pain.
  4. Run the same golden tasks through the candidate and a simpler baseline.
  5. Compare task success, tool correctness, unauthorized actions, p50/p95 latency, cost per successful task, recovery, trace usefulness, and engineering effort.
Decision 11

10. Production-ready means a control system, not a deployment

Security and governance gates

  • Authenticate the human or calling service before the agent.
  • Bind each session to the authenticated user/tenant server-side; do not trust a client-supplied session ID.
  • Give every runtime and tool a least-privilege IAM role.
  • Put deterministic AgentCore/Cedar policy around tool calls; default deny.
  • Use AgentCore Identity/OAuth for delegated SaaS access; avoid sharing broad service credentials.
  • Keep secrets in a secrets manager, not prompts, source code, or memory.
  • Apply document-level permission filtering, but do not confuse ACL-aware retrieval with user authentication.
  • Validate tool inputs, URLs, file paths, and outputs; treat retrieved content and tool descriptions as untrusted.
  • Use Bedrock Guardrails for prompt attacks, harmful content, denied topics, sensitive data, and contextual grounding where supported. Guardrails are one layer, not a substitute for authorization. AWS: Bedrock Guardrails
  • Require approval for irreversible, financial, external-communication, access-control, or high-blast-radius actions.
  • Encrypt at rest and in transit, define retention/deletion, and use private networking where required.
  • Audit who asked, what evidence was retrieved, what the model proposed, what policy decided, what tool executed, and what changed.

Reliability gates

  • explicit timeouts at model, tool, gateway, and workflow boundaries;
  • retries only for retryable failures, with exponential backoff and jitter;
  • idempotency keys and deduplication for side effects;
  • circuit breakers and fallback/partial responses;
  • bounded model/tool loops and token/tool-call budgets;
  • checkpoint/replay or durable workflow for long-running work;
  • compensation or reconciliation when partial side effects occur;
  • load and chaos tests that include downstream throttling, stale credentials, malformed tool results, and process death after a side effect;
  • regional/service quota review and a data-residency decision before using cross-region inference.

The four evidence layers

  1. Deterministic tests: schemas, policy, auth, routing, idempotency, retry, and data isolation.
  2. Offline evals: fixed representative tasks before release; retrieval and generation separated.
  3. Online evals and telemetry: sampled production traces, business outcomes, safety, cost, latency, and drift.
  4. Human review: high-risk actions, ambiguous failures, and evaluator calibration.

AgentCore Evaluations can assess end-to-end goal attainment, tool-call accuracy, and custom dimensions for agents hosted inside or outside AgentCore. It supports online, on-demand, and batch evaluation patterns. AWS: AgentCore Evaluations and AWS: Evaluation types

Decision 12

11. Observability: the PM's fastest route to technical depth

One trace must answer these questions

  1. Which authenticated user/tenant/session initiated the run?
  2. Which application and prompt/model/version handled it?
  3. What retrieval query ran, against which knowledge base/index, with which filters?
  4. Which chunks and source versions were returned and reranked?
  5. Which tool did the model request, with which validated arguments?
  6. What identity and policy decision allowed or denied it?
  7. What did the downstream system return, and was a side effect committed?
  8. Where were time and money spent?
  9. What quality/safety evaluators scored the run?
  10. What user-visible outcome occurred?

AgentCore Observability emits metrics and trace data for runtime, memory, gateway, built-in tools, identity, and policy resources, and is OpenTelemetry-compatible. AWS: Configure AgentCore observability

Langfuse can add application-level traces, prompt versions, datasets, experiments, human/LLM/code evaluations, dashboards, and self-hosting. A useful trace captures model calls, retrieval, tools, inputs/outputs, latency, tokens, cost, and stable operation names. Langfuse observability and Langfuse trace practices

Decision 13

12. Architecture review: the top-1% PM questions

Use these in design reviews and interviews.

Product and scope

  1. What user decision or action improves, and what is the non-AI baseline?
  2. Why does this need an agent rather than search, a form, rules, or a deterministic workflow?
  3. What must the system never do autonomously?
  4. What is the smallest end-to-end slice that proves business value and trust?

RAG and data

  1. What is the authoritative source for every answer class?
  2. What is the freshness SLA, and how are updates/deletions verified?
  3. How are tenant and document permissions enforced before retrieval?
  4. Which metric tells us retrieval failed even when the answer sounds good?
  5. What query types require exact keywords, semantic meaning, graph traversal, or SQL instead of one vector index?

Agent and workflow

  1. Which decisions are probabilistic, and which are deterministic?
  2. What state belongs in AgentCore Memory, DynamoDB, the workflow engine, or the enterprise system of record?
  3. Why is each additional agent necessary, and which measured failure does it fix?
  4. What happens if the process dies after the external action succeeds but before the agent records success?

Tools and integration

  1. Is the model selecting from narrow business tools or a dangerous generic capability?
  2. Is user identity delegated end-to-end, or is a shared service identity hiding authorization gaps?
  3. What is the idempotency key, timeout, retry, quota, and approval rule for each side effect?
  4. Why is MCP useful here—interoperability/discovery/governance—or is it an extra hop around one stable API?

Production and evidence

  1. Show me one complete trace of a success, a denial, a downstream timeout, and a duplicate request.
  2. What fixed evaluation set blocks release? What production signals trigger rollback?
  3. What are the cost and latency budgets per successful task, not per model call?
  4. How do we kill or degrade the agent safely while keeping core business operations available?
  5. Which assumption would make us remove the framework, vector store, or multi-agent design?

Decision 18

17. One-page memory card

  • Bedrock = models and managed AI capabilities.
  • AgentCore = production runtime, tools, identity, memory, policy, observability, and evaluations.
  • Knowledge base = the managed RAG pipeline; vector store = one retrieval component.
  • Better RAG = authoritative data + correct parsing/chunking + metadata/ACLs + retrieval/reranking + separate evals.
  • API = underlying contract; tool calling = model proposes a structured invocation; MCP = standard discovery/invocation layer.
  • API versus MCP is conditional; MCP does not repair a bad API.
  • Lambda = bounded compute/tool; Step Functions = deterministic durable business flow; LangGraph = stateful AI orchestration.
  • DynamoDB = authoritative operational state; AgentCore Memory = conversation-derived context.
  • IAM/Identity authenticates and scopes; Cedar Policy authorizes tool calls; Guardrails handles content/safety; none replaces the others.
  • Single agent first. Add agents only for a measurable boundary or outcome.
  • Frameworks are replaceable. Contracts, policies, evaluations, and traces are the durable product.
  • Production-ready = safe failure, diagnosable failure, bounded cost, reversible change, and evidence-gated release.
Learning boundary. This guide can prepare a decision. It cannot prove that the reader has learned, applied, or retained it. Demonstrate that with the end-of-day architecture review and incident diagnosis.
